# 项目设计踩坑与取舍

本文用于复盘实现过程中的关键问题，并整理为架构和面试讲解素材。

## 1. PostgreSQL 时间类型与 LocalDateTime 转换

**现象**

调用审计的开始时间、结束时间或心跳时间从数据库读取后出现序列化异常、时间精度偏差或绑定参数不受支持。

**根因**

PostgreSQL 的 `timestamp` 与 Java 的 `LocalDateTime` 语义相近，但实体、Mapper参数、JSON序列化若混用 `Instant`、`OffsetDateTime` 或数据库原始时间会产生隐式转换和时区歧义。分页筛选还会把可空时间参数传入动态SQL。

**修复方式**

- 业务实体统一使用 `LocalDateTime` 表达不带时区的数据库本地时间。
- 前端只负责展示格式，后端不要依赖浏览器时区推导业务时间。
- Mapper动态参数只在非空时参与比较，并在接口校验中保证 `startedAfter <= startedBefore`。
- 数据库配置和容器时区保持一致，跨系统边界需要绝对时间时才引入 `Instant`。

**面试讲解点**

不要把日期类型看成纯字段映射问题；要明确是否需要时区、是否参与筛选、是否跨服务传递以及序列化格式。

## 2. 种子 SQL 的类型隐式转换

**现象**

开发profile启动时，种子脚本可能因整数、布尔、枚举文本或状态值类型不兼容而失败，且只在带种子数据的全新库出现。

**根因**

SQL中直接写 `true/false`、数字状态或字符串枚举时，PostgreSQL不会总是按MyBatis实体字段类型进行隐式转换；字段长度、默认值和重复插入条件也会影响幂等性。

**修复方式**

- 种子状态统一使用实体实际存储的字符串值，如 `ENABLED`、`DISABLED`、`SUCCEEDED`。
- 使用 `WHERE NOT EXISTS` 或唯一约束保证重复启动不会重复插入。
- 建表和种子分为 `schema.sql` 与 `schema-dev.sql`；生产profile不加载种子。
- 新库启动时先验证主键、外键、逻辑删除字段和枚举文本是否一致。

**面试讲解点**

开发种子也属于部署输入；应让它幂等、可复现，并与生产Schema边界分离。

## 3. 分页动态 SQL

**现象**

某些筛选组合返回数据正常，单独筛选、分页第二页或关键字查询时发生分页错位、参数未传入或计数与数据页不一致。

**根因**

动态SQL把筛选条件、COUNT和LIMIT/OFFSET写在不同代码块中；可空参数、SQL分页表达式和Java分页页码容易偏移。`CAST`等写法若跨数据库也可能不一致。

**修复方式**

- HTTP页码统一从1开始，Mapper接收已计算的 `offset = (page - 1) * size`。
- 统一约束 `size <= 100`，避免一次性查询过大。
- COUNT与数据查询使用相同筛选条件，只负责各自用途。
- PostgreSQL查询使用明确的参数和动态 `<if>`，并保留租户、逻辑删除、排序字段。
- 缓存分页结果时，页码、条数和所有筛选参数都进入key。

**面试讲解点**

分页不仅是`LIMIT/OFFSET`，还包括计数一致性、排序稳定性、参数白名单和租户隔离。

## 4. 租户隔离设计

**现象**

同一个接口若缺少租户条件，可能在缓存或数据库中读取到另一个租户的Server、Tool或调用记录。

**根因**

租户上下文分散在请求、JWT和缓存时容易被缺失或拼接错误；Mapper只按主键查询会绕过租户边界。

**修复方式**

- 用户认证后的主体租户优先进入 `TenantContext`；开发profile可保留受控的 `X-Tenant-ID`兜底。
- Mapper提供 `tenantId + id`、`tenantId + code`等租户限定查询。
- 注册、编辑、删除和状态变更都校验当前租户。
- Caffeine key包含tenant ID，不提供跨租户访问接口。
- 缓存失效按tenant key前缀完成，不清空其他租户缓存。
- 生产环境租户来源应由可信网关注入，不能由普通客户端任意传参决定。

**面试讲解点**

租户隔离是横切安全约束，应同时落在认证上下文、业务Service、SQL和缓存四层。

## 5. Caffeine本地缓存一致性取舍

**现象**

写操作之后短暂再次看到旧分页数据，或多实例部署时某实例比另一个实例更晚失效。

**根因**

缓存是进程内副本，写操作只能主动失效当前进程；并发读写可能在失效和回源之间交错。

**修复方式**

- 默认TTL为5分钟，最大条数分别为1000，均可环境变量覆盖。
- Server和Tool分页分别缓存，key包含租户和所有筛选参数。
- 注册、编辑、删除、健康更新和状态切换成功后主动失效对应租户缓存。
- 数据库仍是事实来源；缓存仅是短期加速副本，不写入缓存作为持久业务状态。

**一致性权衡**

这是最终一致策略：能用主动失效和TTL控制绝大多数场景，但无法保证外部数据库直写或跨实例写入立即全局一致。需要强一致时应引入分布式缓存、失效消息或数据库版本校验，而不是继续提高本地TTL。
